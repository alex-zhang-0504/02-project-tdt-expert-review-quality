# 技术项目经理与管理员统一配置

本机唯一账号源是`config/project-managers.json`。修改文件后登录权限实时读取；新任务默认采用最新配置，也可选择JSON导入更新。已有任务须在卡片「修改技术项目经理名单」导入，才更新该任务的主观评价范围。Excel仅作为生成初始配置的来源。

文件结构如下，仅使用虚拟人员举例：

可复制字段结构的文件为[project-managers.example.json](../config/project-managers.example.json) 。示例不自动启用；正式使用时填写实际人员，保留系统首次登记的管理员及其编号，不用示例覆盖已有账号。真实配置仍排除Git。

```json
{
  "version": 1,
  "users": [
    {"name": "虚拟管理员", "employee_id": "001000", "role": "admin", "enabled": true, "owner_ids": []},
    {"name": "虚拟技术项目经理甲", "employee_id": "001001", "role": "manager", "enabled": true, "owner_ids": []},
    {"name": "虚拟技术项目经理乙", "employee_id": "001002", "role": "manager", "enabled": false, "owner_ids": []}
  ]
}
```

- `name`：姓名，须与飞书原文件所有者姓名一致。启用的人员不能重名。
- `employee_id`：工号，必须带英文双引号，保留前导零。同一人的工号保持不变；人员替换时新增工号并停用旧人，不把旧工号改成另一个人。
- `enabled`：`true` 表示启用，`false` 表示停用，不加引号。
- `role`：`admin`为管理员，`manager`为技术项目经理；管理员可代填；有本人项目及参评交集时也分配本人问卷，角色不免除评价任务。
- `owner_ids`：历史原文件所有者关联，仅用于冲突校验，不能覆盖姓名匹配；新任务直接保存归属快照，不在读取页面新增全局绑定。工号仅作为后台编号，登录及业务页面不展示、不要求输入。

新任务纳入本次名单中启用的人员，管理员与普通技术项目经理按相同项目交集规则分配问卷。导入完整配置可修改角色、姓名及启用状态，须保留启用管理员。停用或未列出的既有技术项目经理不能登录，但原问卷及报告关联保留。兼容旧三字段文件，此时已有管理员权限不变，是否分配问卷仍取决于是否纳入任务及本人项目交集。

飞书报告仍从原文件所有者获取姓名。姓名唯一匹配本任务启用人员时自动关联工号；历史关联与姓名不一致即拦截，不能通过手工选择另一个姓名绕过。缺失姓名、重名、停用、未纳入等异常需核对配置或重新读取来源。已确认任务也校验原所有者与归属快照，冲突期间不分配问卷、不开放个人数据、不生成完整主观结果。确认归属的来源、操作者与前后值保存在任务的`ownership_history`中。本地 Excel 报告无飞书原文件所有者，仍需指定归属。

导入后更新同一份`config/project-managers.json`，不再维护运行名单副本。旧`var/multi-user/accounts.json`仅作为迁移归档。已确认任务归属与问卷不随新任务名单重新分配。真实配置排除Git，须随本机备份保存，不会跨电脑自动同步。隔离测试目录仍使用目录内的`accounts.json`。

## 已有任务修改名单

管理员在未完成任务卡片点击「修改技术项目经理名单」，选择更新后的`project-managers.json`，核对人员及启用状态后点击「确认更新名单」。新建任务时的导入入口继续保留。

名单修改仅调整本期主观问卷任务及其汇总：取消人员的原问卷、修改历史保留，但不计入本期有效主观结果；不转交问卷或继承他人答案。客观报告、评审人范围、名单确认和客观得分保持不变，评分参数也不变。没有有效主观评价时不能生成完整总分，不以零分补齐。

账号停用会影响登录；其他任务的历史名单快照不被改写。已完成任务只读。页面更新统一配置与当前任务名单；若选择的是另一份外部文件，不反写那个外部文件。
